# Credential Storage and Keychain Policy

**Status:** Enforced
**Date:** 2026-09-15
**Scope:** How Apple Pi protects provider API keys, and why the macOS keychain prompt is expected

## The rule

Never make Apple Pi bypass the operating system keychain. Specifically, do not add:

- the Chromium `use-mock-keychain` command-line switch,
- `safeStorage.setUsePlainTextEncryption(true)`,
- any fallback that writes credentials in plaintext when encryption is unavailable.

`apps/desktop/src/shared/security-policy.test.ts` fails the build if either API appears
in the main process, so this policy is enforced rather than merely documented.

## Why

Provider API keys are persisted by `CredentialBroker` in
`apps/desktop/src/main/credential-broker.ts`. On macOS and Windows, `storagePolicy`
returns `persistent` whenever `safeStorage.isEncryptionAvailable()` is true, and the
ciphertext is written to `credentials.json` (mode `0600`) under the app's `userData`
directory. Electron's `safeStorage` is backed by Chromium's OSCrypt, which derives its
key from a keychain item named `<app name> Safe Storage`.

The mock keychain is the trap. It does not make `isEncryptionAvailable()` return false;
it keeps returning `true` while replacing the keychain-derived key with a well-known
constant. `CredentialBroker` would therefore stay on the `persistent` path and keep
writing `credentials.json`, but the file would be decryptable by anything that can read
it. That is strictly worse than plaintext, because the storage still looks protected.

The same reasoning applies to Chromium profile encryption: cookies and web storage are
encrypted with a key from the same keychain item.

## The macOS prompt is expected behaviour

On macOS, the first credential write (and the first launch after the app's code
signature changes) shows:

> Apple Pi wants to use your confidential information stored in "… Safe Storage" in your keychain.

This prompt is macOS asking permission for the app to read its own encryption key. It is
generated by the credential broker's use of `safeStorage`, not by a network request, and
the entered password is consumed by the keychain handshake rather than by application
code.

### Legitimate ways to stop it reappearing

- **Sign releases with a stable Developer ID.** The keychain access control list is bound
  to the code signature, so an ad-hoc or changing signature invalidates it on every
  build. Tag builds are signed and notarized by the package workflow; local
  `package:mac` builds are not, so they will re-prompt after each rebuild.
- **Do not rename the application or change `appId`.** The keychain item is derived from
  the app name, so a rename creates a new item and prompts again.
- Clicking **Always Allow** records the decision for the current signature. **Deny** is
  not remembered and the prompt returns on the next launch.

Do not "fix" the prompt by disabling the keychain. The only acceptable alternative, if
persistence is ever deliberately dropped, is a session-only policy: change the
`storagePolicy` decision in `credential-broker.ts` so credentials stay in memory and the
user is told that keys will not survive a restart.

## Related constraint: `app.setName` moves user data

`app.getPath("userData")` is derived from the application name and holds both
`catalog.json` (workspaces and default model) and `credentials.json`. Calling
`app.setName(...)` therefore relocates the credential store: the app will look like it
forgot every saved provider key, and the old encrypted file is orphaned rather than
migrated. Set the name before shipping, then leave it alone, and migrate existing files
explicitly if the name ever has to change.
